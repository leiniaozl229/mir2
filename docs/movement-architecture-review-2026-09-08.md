# 移动机制审计与修复（2026-09-08）

基线：`3fec4c6`。复核任务「Review试玩并更新文档」中最近几轮移动修复，并检查当前源码、实际 Crystal 素材、运行网关和开源客户端。审计发现原实现存在多个机制缺陷，之前的验证不能支持“移动已修复”。下文保留修复前证据，并记录本轮按建议方案完成的实现与验证。

## 修复结果

生产移动链路已完成机制重构：

- 浏览器为移动、攻击和施法生成单调递增的 `actionId`，每个请求同时携带当前 `mapGeneration`。网关将旧协议 GOOD/FAIL 关联为 `{type:"actionResult",actionId,kind,accepted,x,y,reason,mapGeneration}`；本地拒绝也返回动作身份。前端不再从原始 `legacy` 状态帧推断移动成功。
- 自机在发送移动时只预测一段动作，角色位移、六帧步态和相机共用同一个 `startedAt` 与 600ms 周期。下一步同时等待当前动作播放结束和对应 ACK；拒绝会回滚到网关返回的权威坐标，命令错误会终止当前移动意图，确认超时会触发重连同步。
- 键盘、右键、点击寻路、目标追踪和地面物品追踪统一进入动作调度。pending 期间仍更新输入意图，动作完成后再取最新意图。右键采用等距地图投影下的八方向相似度、12px 死区和边界滞回；点击寻路加入直行偏好、转向代价和稳定平局规则。
- Crystal 人物与怪物恢复资源原方向编号，0/2/4/6 分别对应上/右/下/左。人物走路使用 `32 + 6*d + f`，跑步使用 `80 + 6*d + f`；女性身体/头发偏移 808、女性武器偏移 416 保持不变。
- 自机当前装备的站立、走路、跑步八方向资源会提前加载。动作切换加载期间保留上一个有效姿态。远端角色把连续移动事件放入独立队列，在前一段 600ms 位移完成后按顺序播放，后续目标不会覆盖当前段；跨越超过单次走跑距离或队列积压到八段时直接同步到最新权威格。

验证结果：`npm run test:web`、`npm run build`、Python 网关契约 9 项和 C# GatewayRegression 均通过；`node tools/movement_architecture_audit.mjs` 对生产移动模型执行方向、路径、ACK/动画门控及集成边界检查并输出 [implementation.json](../.runtime/reports/movement-audit-20260908/implementation.json)。更新后的真实 WebSocket 回放完成 22 次走跑、0 次拒绝并回到起点，相邻动作启动间隔为 600–602ms，见 [movement-replay.json](../.runtime/reports/movement-replay.json)。动作校验页已逐格检查八方向走路和跑步素材，朝向与方向编号一致。可见 Chrome 实机试玩又通过 15 项检查，覆盖人物首帧可渲染、键盘单步与长按、直线点击、近水平右键跑步、半程渲染位置、人物/相机锚点、动作关联和返程复位；人物预载后约 `89.8ms` 可渲染，报告见 [Agent 实机试玩 latest](../.runtime/reports/agent-playtest/latest.json)。

尚未完成视频级逐帧录制、冷缓存耗时量化、900ms 高延迟网络注入及多人同屏长距离移动，因此当前结论覆盖机制修复、生产构建、网关实包、素材方向和一轮可见浏览器自动试玩；剩余场景继续按文末验收矩阵执行。

## 修复前核心证据

| 问题 | 修复前实现及证据 | 对玩家的影响 |
| --- | --- | --- |
| P1：收到确认就续发，动画仍需 600ms | `play.ts:314,535`：按键确认后等 45ms，右键/点击路径立即续发。真实网关测试 12 次移动全部接受，ACK 延迟 152–201ms，发送间隔中位数约 199.5ms | 连续移动速度取决于网络及服务端处理速度，走跑动画来不及完成 |
| P1：每次确认重写当前移动终点与计时 | `online-actors.ts:48–52` 从当前显示位置重新插值到最新权威格，重新播放六帧 | 动画前两帧反复重播；停止输入后还需追赶多格；转向时身体朝向与显示轨迹分离 |

### 1. 600ms 配置没有形成当前运行环境的移动限速

`GameSvrConf.cs:1920` 默认 `CloseSpeedHackCheck = true`；`PlayObject.Attack.cs:1301,1377` 在该开关为 false 时才进入走跑间隔检查。虽然 `WalkIntervalTime`、`RunIntervalTime` 都配置为 600，不能据此认定服务端每 600ms 才接受一步。

本轮使用已验证的专用探针角色，步行 3 步出、3 步回，跑步 3 步出、3 步回。12 次全部接受、0 拒绝，起终点均为 `(286,618)`。连续发包间隔约 200ms，移动阶段只有 12 个 `+GD`，没有自机 `entity` 移动消息。原始记录：[live-cadence.json](../.runtime/reports/movement-audit-20260908/live-cadence.json)。

`PlayObject.Message.cs:1413,1433` 明确排除向玩家自己广播 WALK/RUN。因此此前文档中“自机先收到 entity，随后 +GD，二者分别启动人物与相机”的解释不适用于这条实际链路。自机使用动作确认来推进权威坐标有协议依据。

600ms 作为客户端六帧动作的基准时长有参考依据。问题集中在缺少客户端动作节拍约束，以及把服务端确认间隔与视觉动作时长混为一谈。

### 2. 已从修复前业务源码复现滑行与转向偏差

初次审计脚本直接转译修复前 TypeScript，用可控时钟、显示对象替身和真实资产元数据执行输入函数及 `OnlineActor.update/tick`。它验证逻辑，不代表浏览器 GPU/FPS 或实测图片下载耗时。脚本现已改为执行修复后的生产移动模型和集成边界检查。

- 注入 150ms 间隔的四次单格向右移动：显示帧反复 `68 → 69 → 68 → 69`；最后一次更新从显示坐标 `11.265625` 插值到逻辑坐标 `14`，一个“步行动作”要走 **2.734375 格**。
- 向右一步尚未显示完成，在 150ms 时收到向下一步：逻辑方向为南，实际新插值向量为 **右 0.75 格、下 1 格**。仅用相邻权威格计算方向无法修正这条已被改写的显示轨迹。
- 注入 300ms 图片加载延迟：299ms 时人物纹理为空，300ms 就绪后直接显示第 4 个步态帧。该数值为控制实验，尚未量化真实浏览器冷缓存耗时。

证据：[input-render.json](../.runtime/reports/movement-audit-20260908/input-render.json)。人物和相机仍各自持有一份 motion 与起始时间（`map-view.ts:23,159`）；使用同一个常量和同一个事件入口，仍不足以保证共享同一份动作状态。

### 3. 输入错误可以脱离服务端复现

空地 `(10,10)` 点击 `(16,10)`，当前寻路输出：

```text
(10,10) → (11,9) → (12,8) → (13,7) → (14,8) → (15,9) → (16,10)
```

路线向上偏了 3 格。等代价 BFS 找到了最少格数路径，但固定邻居顺序没有直行或最少转向偏好。八方向网格还需明确直行、斜行代价与平局规则。

以当前右键参考点 `(400,300)` 为例，指针在 `(650,301)`，仅低 1 像素也会输出 `(dx=1,dy=1)`，连续向右下跑。应基于投影后的八个方向向量划分扇区，并设置中心死区与边界滞回。`play.ts:594` 还会在 pending 期间直接丢弃新点击；输入意图应持续接收，由调度器决定何时执行。

### 4. 素材方向已交叉核验，帧表与导出保持有效

实际资源来自 Crystal `.Lib`，使用 compact CArmour 布局。当前 Walking `32 + 6*d + f`、Running `80 + 6*d + f` 与 [Crystal 玩家帧表](https://github.com/Suprcode/Crystal/blob/0e315fe327192afe52c3d7357ddd1f5b7e26c5b8/Client/MirObjects/Frames.cs#L157) 一致。女性身体/头发偏移 808、武器偏移 416 也与其客户端相符。

22 个衣服、头发、武器库的男女站立/走路/跑步 **5,632 帧**已与锁定原 `.Lib` 解码结果比对：像素、尺寸、偏移全部一致，源文件哈希全部一致，0 错误。[机器校验](../.runtime/reports/movement-audit-20260908/actor-export-validation.json)。

原图中方向 0 是背面朝上，2 是侧面朝右，4 是正面朝下，6 是侧面朝左；修复前向右选帧 `68`，正确首帧为 `44`。[八方向对照图](../.runtime/reports/movement-audit-20260908/direction-contact-sheet.png)、[男女分层六帧图](../.runtime/reports/movement-audit-20260908/movement-layers-six-frames.png)。Crystal 直接按方向乘 stride 选帧：[PlayerObject.cs](https://github.com/Suprcode/Crystal/blob/0e315fe327192afe52c3d7357ddd1f5b7e26c5b8/Client/MirObjects/PlayerObject.cs#L761)。

旧式 Hum.wil 使用另一套带空位的帧布局；本项目应显式记录资源布局，防止将 Hum 名称、compact 帧表和方向补偿混用。`actors.ts` 预览页本轮已接入在线渲染使用的 `visualDirection`，并增加八方向跑步校验入口。

### 5. 攻击确认错配已离线复现

`GatewaySession.cs:237,282` 会拒绝前一个攻击尚待确认时的移动请求；`508–512` 又会按真正的 pending 类型消费 GOOD。前端 `play.ts:535` 缺少这个关联，`555` 的错误处理保留了移动 pending。

执行修复前前端处理函数，注入上述合法网关事件顺序：攻击占线 → 用户移动 → 网关拒绝移动 → 攻击 `+GD` → 再次移动。结果为网关位置仍 `(10,10)`，前端凭空更新到 `(11,10)`，下一次请求 `(12,10)` 被拒后 pending 无法释放。证据：[action-ack-repro.json](../.runtime/reports/movement-audit-20260908/action-ack-repro.json)。这是源码控制实验，本轮未对真人角色执行攻击切换。

## 实施方案与落地状态

开源旧协议客户端已有可借鉴的动作模型：本地先开始动作，发包后锁住在途动作，GOOD 解锁、FAIL 回滚；下一动作同时等待动画结束与服务端确认。[Actor.pas 本地动作](https://github.com/lzxsz/MIR2/blob/98711dad31567d9a7e272956f6c5a2487000848b/GameOfMir/Client/Actor.pas#L1467)、[ClMain.pas 发包与确认](https://github.com/lzxsz/MIR2/blob/98711dad31567d9a7e272956f6c5a2487000848b/GameOfMir/Client/ClMain.pas#L3008)。该仓库自述包含 1.5/1.76；它作为实现参照，不能替代当前 OpenMir2 的协议验证。

1. **动作协议：已完成。** 浏览器与网关使用 `actionId + kind + mapGeneration` 关联移动、攻击、施法的结果；原始 `legacy` 只作诊断数据，超时进入重连同步。
2. **本地移动控制：已完成。** 一次只预测一段，下一段等待动画时限和 ACK，所有移动输入共用一个 pending 动作与意图调度入口。
3. **视觉时间线：已完成。** 自机角色、分层帧和相机使用同一个动作起点；远端连续移动按事件排队，当前段不会被改写。
4. **输入与素材：已完成。** 右键扇区、死区、滞回、稳定寻路、Crystal 原方向映射、八方向预载和异步姿态保留均已落地。
5. **浏览器验收：已完成首轮。** 可见 Chrome 已覆盖单步半程、连续键盘、点击和右键走跑；视频级逐帧录制、冷缓存、网络延迟注入和多人同屏长距离移动仍待执行。

## 已替换的验证方式

旧 `movement_replay.mjs:143,151` 每次先等待 ACK，再额外 sleep 600ms；历史报告实际间隔为 700–841ms。脚本现以动作开始时间为基准，同时等待 ACK 和 600ms 动作截止点，执行节拍与浏览器控制器一致。最新 22 次回放的相邻动作启动间隔为 600–602ms。

`frontend_regression.mjs` 现直接执行生产 `movement-model.ts`，覆盖方向投影、直线路径和 ACK/动画双门控，同时检查角色、相机、预载和类型化协议的集成边界。它仍不能替代以下浏览器场景：

| 场景 | 可判断的通过条件 |
| --- | --- |
| 男女、裸体/穿衣/持武器，八方向走跑 | 实际 PNG 身体朝向与每段路线一致；每段六帧索引完整、分层同步 |
| 长按键盘、长按右键、远处点击 | 使用统一发送节拍；一段走一格或跑两格；没有反复重置前两帧 |
| 直线点击、斜线、拐角、连续改目标 | 空地不产生无理由折线，转向在明确格点发生，输入不会因 pending 丢失 |
| 0/150/300/900ms ACK 延迟与抖动 | 早到 ACK 不打断当前动作；迟到 ACK 不叠加固定延迟；无无界积压 |
| 攻击/施法后移动、网关拒绝、迟到 ACK | 按 actionId 归属；无虚假权威坐标；可恢复，不串配确认 |
| 撞墙、门、死亡、换图、断线 | 明确取消或校正当前动作；旧地图/旧连接事件不能重启动作 |
| 首次载入与首次转向 | 人物不被清空；不因图片异步加载跳过大半步态 |
| 人物与镜头 | 每帧来源于同一动作采样，记录屏幕锚点偏移并检查持续漂移 |

当前自动回归、资源文件存在、动作页截图和网关接受次数共同缩小了风险范围，仍需用以上浏览器场景完成最终人工观感验收。
